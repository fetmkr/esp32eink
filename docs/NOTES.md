# 실측 기록

XIAO ESP32-S3 Plus + Seeed EE05 보드 + Good Display GDEY0426T82 (4.26인치, 800x480, SSD1677)

측정 날짜 2026-08-19. 모두 이 보드에서 직접 재거나 원문에서 확인한 것이다.

## 핀

회로도 `schematic/XIAO_ePaper_Display_Board_EE05_V1.0_SCH.pdf` 와
Arduino esp32 코어 `variants/XIAO_ESP32S3_Plus/pins_arduino.h` 에서 확인.

| 신호 | XIAO 핀 | GPIO | FPC 핀 |
|---|---|---|---|
| SCK | D8 | 7 | 12 |
| MOSI | D10 | 9 | 11 |
| CS | D7 | 44 | 13 |
| DC | D16 | 10 | 14 |
| RST | D11 | 38 | 15 |
| BUSY | D3 | 4 | 16 |
| 패널 전원 | D6 | 43 | 보드 내부 |
| 버튼1 | D1 | 2 | KEY 블록 K2 |
| 버튼2 | D2 | 3 | KEY 블록 K3 |
| 버튼3 | D9 | 8 | KEY 블록 K4 |
| LED | - | 21 | XIAO 모듈 위, 활성 LOW |

D6(GPIO43)을 HIGH 로 안 올리면 BUSY 가 안 풀린다.

## 갱신 시간

| 방식 | 그림 보내기 | 갱신 | 눈에 보이기까지 |
|---|---|---|---|
| 전체 (800x480) | 183ms | 1700ms | 1.88초 |
| 부분 (800x480) | 92ms | 405ms | 0.50초 |
| 부분 (시계 칸만 256x44) | 3ms | 406ms | 0.42초 |

- 갱신 시간은 창 크기와 무관하다. 480줄이든 60줄이든 407ms 로 같다.
- 전체 갱신 1700ms 는 이미 빠른 쪽 파형이다. `useFastFullUpdate = true`.
  규격상 보통 전체는 3.5초, 빠른 전체는 1.5초.

## SPI 속도

GxEPD2 기본값은 4MHz (`GxEPD2_EPD.cpp` 24줄).

| 속도 | 48000바이트 보내기 |
|---|---|
| 4MHz | 180ms |
| 8MHz | 124ms |
| 16MHz | 96ms |
| 20MHz | 90ms |
| 26MHz | 91ms |

20MHz 위로는 안 빨라진다. 바이트를 하나씩 보내는 함수 호출 비용이 벽이다.
한 바이트에 1.9마이크로초인데 선로에 실리는 시간은 0.4마이크로초뿐이다.

## 하면 안 되는 것

### GxEPD2 의 writeImageAgain 을 줄이지 말 것

`drawImage` 는 안에서 이렇게 돈다.

    writeImage      -> refresh -> writeImageAgain

`writeImageAgain` 은 이전 화면(0x26)과 현재 화면(0x24) 두 곳에 다 쓴다.
전송을 아끼려고 `writeImageToPrevious`(0x26 만) 로 바꾸면 다음 부분 갱신이
엉뚱한 차이를 계산해서 화면이 겹쳐 보인다. 실제로 그렇게 만들었다가 되돌렸다.

### 부분 갱신을 두 걸음으로 나누지 말 것

"창을 바탕색으로 한 번 민 뒤 내용을 그리면 시작 상태가 깨끗해진다"고 예상해서
만들었는데, 미는 동작이 눈에 그대로 보여서 숫자가 깜박였다. 기본 한 걸음이 맞다.

## 온도로 파형 고르기 — 이 패널에는 안 통함

데이터시트 6.9절: 칩 안 OTP 에 파형이 34벌 있고 온도로 고른다.
0x22 의 0x20 비트를 끄면(0xFC 대신 0xDC) 0x1A 로 써넣은 온도가 쓰인다.
GxEPD2 도 전체 갱신을 빠르게 할 때 이 수법을 쓴다 (0x1A 에 0x5A = 90도).

실측: -20도부터 40도까지 바꿔도 갱신 시간이 418ms 로 똑같았고 화면도 같았다.
이 패널은 부분 갱신 파형을 한 벌만 담고 있다.

## 파형을 직접 써넣기 — 되긴 됨

## 시계 건너뛰기 (2026-08-19 측정)

3분 동안 재보니 정확히 3번, 전부 60초 지점, 전부 3초씩 건너뛰었다.

    59.5s  10 -> 13 (3초)
   120.5s  11 -> 14 (3초)
   181.5s  12 -> 15 (3초)

원인은 잔상 털기(전체 갱신)다. 2.06초가 걸리는 동안 시계가 멈추니 3초를 건너뛴다.
그 밖에 불규칙한 건너뛰기는 없었다. 더 크게 건너뛴 것은 시리얼을 열거나 펌웨어를
올려서 보드가 리셋됐을 때였다.

### 정한 값

부분 갱신 300번(5분)마다 전체 갱신 한 번.
제조사 권고(5~6번마다)보다 50배 넉넉하다. 사용자가 초 표시를 유지하기로 정했다.
잔상이 눈에 거슬리면 줄인다. 시리얼로 `G<숫자>` 를 보내면 바로 바뀐다.

전자잉크 시계 프로젝트들은 대개 초를 안 보여준다.
1분마다 부분 갱신, 1시간마다 전체 갱신이 흔한 방식이다.

## 시계가 멈춰 보이던 진짜 원인 — 시리얼 출력 (2026-08-19)

증상: 시계가 뜨문뜨문 가다가 멈춤. 그런데 시리얼을 열어 읽고 있으면 잘 감.

원인은 화면이 아니라 USB 출력이었다.

    // HWCDC.cpp
    static uint32_t tx_timeout_ms = 100;
    const uint32_t max_consec_timeouts = 20;   // 100ms x 20 = 최대 2초

USB 가 꽂혀 있는데 아무도 읽어가지 않으면 출력 버퍼가 차고, Serial.printf 한 번이
최대 2초까지 멈춰 선다. 시계가 1초마다 두 줄을 찍고 있었으니 (GxEPD2 진단 줄과
내가 넣은 줄) 한 번에 최대 4초를 붙잡혔다.

### 고친 것

    Serial.setTxTimeoutMs(0);         // 안 나가면 기다리지 말고 버린다
    display.init(0, true, 2, false);  // 첫 인자 0 = GxEPD2 진단 출력 끔
    bool clockLog = false;            // 시계 로그 기본 끔. 시리얼 p 로 켠다

### 검증

포트를 닫고 116초 뒤 다시 열어 눈금을 비교했다.

    닫기 직전   16:41:05  눈금 11
    다시 열 때  16:43:01  눈금 127

116초에 116눈금. 하나도 안 빠졌다. 보드는 리셋되지 않았고 시각과 바탕색도 유지됐다.

### 교훈

증상만 보고 화면 문제라고 단정해서 잔상, 파형, 온도까지 파고들었다.
"연결하면 가고 끊으면 멈춘다" 는 관찰 하나로 소프트웨어 문제인 것이 정해졌다.
언제 증상이 달라지는지 먼저 물었어야 했다.

## 회색 4단계 바탕 + 흑백 시계 (2026-08-19)

바탕 그림은 회색 4단계로 곱게 그리고, 시계 칸만 흑백 부분 갱신으로 매초 민다.
되긴 되는데 함정이 하나 있었다. 그게 이 글의 핵심이다.

### 핵심 발견 — 부분 갱신은 화면 전체를 훑는다

창(0x44, 0x45 로 정하는 영역)은 **데이터를 쓰는 자리**일 뿐이다.
실제로 움직이는 픽셀은 **두 화면 메모리 값이 서로 다른 곳**뿐이다.

근거 두 가지, 둘 다 실측이다.

1. 창을 480줄에서 60줄로 줄여도 갱신 시간이 407ms 로 똑같았다.
   창만 훑는다면 시간이 줄어야 한다.
2. 회색으로 그린 뒤 시계 칸만 밀었더니 화면 전체가 망가졌다.
   두 메모리를 같은 값으로 채우고 나니 시계 칸만 바뀌었다.

원래 흑백만 쓸 때는 이 성질이 안 보인다. 칸 밖은 두 메모리가 늘 같아서
저절로 "바뀐 곳 없음" 이 되기 때문이다.

### 회색과 흑백은 같은 메모리를 다르게 읽는다

| 0x26 | 0x24 | 회색 모드에서 | 흑백 부분 갱신에서 |
|---|---|---|---|
| 1 | 1 | 흰색 | 안 움직임 |
| 1 | 0 | 연한 회색 | 흰색 -> 검정 으로 움직임 |
| 0 | 1 | 진한 회색 | 검정 -> 흰색 으로 움직임 |
| 0 | 0 | 검정 | 안 움직임 |

회색 그림에서 연한 회색과 진한 회색을 쓴 자리가, 흑백 기준으로는 전부
"바뀐 곳" 이다. 글자 가장자리가 바로 그 자리다. 그래서 처음에 화면 전체가
검게 깔리고 글자가 테두리만 남는 모양이 나왔다.

### 순서

1. 회색 4단계로 화면 전체를 그린다 (4.41초).
   시계 칸은 순수한 검정과 흰색으로만 그린다. 회색이 섞이면 안 된다.
2. SWRESET(0x12) 으로 흑백 설정으로 되돌린다.
   회색용으로 바꿔 뒀던 전압(0x03, 0x04, 0x2C)과 파형(0x32)이 기본값이 된다.
3. **화면 메모리 두 장을 같은 값으로 채운다.** 이게 빠지면 다 망가진다.
   눈에 보이는 회색 그림은 전자잉크라 그대로 남는다.
4. 매초 시계 칸에만 0x26 에 이전 모습, 0x24 에 지금 모습을 쓰고
   부분 갱신한다 (0.41초).

`src/gray/epd_mixed.h` 의 initBW() 와 fillBothPlanes() 가 2번과 3번이다.
GxEPD2_4G 는 회색에서 흑백으로 넘어갈 때 전체 갱신을 강제하므로 그대로 못 쓴다.
그 라이브러리가 하는 일을 뜯어 필요한 부분만 다시 적었다.

### 값

| 항목 | 값 |
|---|---|
| 회색 전체 갱신 | 4.41초 |
| 흑백 시계 갱신 | 0.41초 |
| 회색 화면 한 장 | 96000바이트 (한 픽셀 2비트) |
| 회색 폰트 5가지 | 107KB |

## 움직이는 것을 그리는 법 (내비게이션식)

지도는 고정이고 배만 움직이는 화면. 항적 띠 데모로 확인했다.
`src/gray/main_gray.cpp` 의 pushRegionsBW() 참고.

### 자리를 여러 개 써놓고 갱신은 한 번만

부분 갱신은 화면 전체를 훑는다. 그러니 창을 여러 번 잡아 각각 값을 써넣고
갱신은 한 번만 부르면, 여러 자리가 같이 움직인다.

    setRamArea(시계 칸);  writeWindow(0x26, 이전);  writeWindow(0x24, 지금);
    setRamArea(항적 띠);  writeWindow(0x26, 이전);  writeWindow(0x24, 지금);
    updatePartBW();       // 한 번만

갱신을 두 번 부르면 0.41초가 두 번 든다. 한 번이면 0.41초로 끝난다.

실측: 시계만 411ms, 시계 + 항적 띠(704x40) 424ms. 13ms 밖에 안 는다.
그 13ms 는 배 그림을 메모리에 보내는 시간이다. 갱신 시간 자체는 그대로다.

### 움직이는 자리는 순수 흑백이어야 한다

회색이 한 점이라도 섞이면 그 자리를 흑백 부분 갱신이 "바뀐 곳" 으로 읽어서
엉뚱하게 움직인다. 배가 지나갈 띠와 시계 칸은 검정과 흰색만 쓴다.

### 창은 8의 배수

x 와 폭이 8의 배수여야 한다. 컨트롤러가 바이트 단위로 주소를 잡는다.

### 앞으로 만들 때 순서

1. 고정된 배경을 한 번 그린다 (회색이면 4.4초, 흑백이면 1.9초).
   움직일 자리는 순수 흑백으로 그려둔다.
2. 두 화면 메모리를 같은 값으로 채운다 (fillBothPlanes).
   이걸 빼먹으면 첫 부분 갱신에서 화면 전체가 망가진다.
3. 움직일 때마다: 각 자리에 이전 모습(0x26)과 지금 모습(0x24)을 쓰고,
   갱신은 한 번만 부른다.
4. 이전 모습 버퍼를 지금 모습으로 갱신해 둔다.
5. 잔상이 쌓이면 배경부터 전체 갱신을 다시 한다.
